# 요구사항 시작: $ARGUMENTS

이 스킬은 설계와 계획만 만든다. 개발자가 승인하기 전에는 코드를 고치지 않는다.

## 1. 요구사항 파악 (코드 변경 없음)
- `docs/requirements.md`에서 $ARGUMENTS 행과 관련 결정 사항(D-xx), 관련 비기능 요구사항(NFR-xx)을 찾는다
- 지금 코드에서 관련 패키지·테이블·API를 읽고, 이미 있는 것과 새로 필요한 것을 나눈다
- 요구사항만으로 정할 수 없는 열린 질문을 목록으로 만든다

## 2. 설계 스펙 작성
`docs/design/$ARGUMENTS.md`에 다음을 쓴다.
- API: 메서드, 경로, 요청·응답 DTO, 오류 코드와 HTTP 상태
- 엔티티·스키마 변경: 새 마이그레이션, 제약, 인덱스
- 트랜잭션과 동시성: 무엇을 어떤 락·제약으로 지키는지 (NFR-01)
- 테스트 시나리오: 정상, 예외, 경계값, 동시성
- 열린 질문과 제안하는 답

여기서 멈추고 개발자에게 설계 승인을 요청한다.

## 3. 구현 계획 작성 (설계 승인 후)
`docs/plans/$ARGUMENTS.md`에 작업 단위 T1, T2, ...를 쓴다. 단위마다:
- 바꿀 파일과 메서드
- 먼저 작성할 테스트
- 완료 확인 명령 (예: `cd backend && ./gradlew test --tests "*EnrollmentServiceTest"`)
- 앞 단위에 대한 의존

여기서 멈추고 개발자에게 계획 승인을 요청한다.

## 4. 작업 단위의 크기
- implementer가 그 단위 하나만 보고 구현할 수 있을 만큼 구체적으로 쓴다
- reviewer가 계획과 diff를 비교해 판정할 수 있게, 바뀌어야 할 동작을 검증 가능한 문장으로 쓴다
- 한 단위는 한 계층 또는 3개 이하 파일을 넘지 않게 나눈다
